# 文档分块

检索的单位不是文档，而是 chunk。融合背景见 [混合检索](hybrid-search.md)。

## 切分规则

按 Markdown 标题层级与段落切分，识别代码围栏（fence）以避免在代码块中间切开。
每个 chunk 记录它的标题路径，因此命中结果能定位到具体章节而不只是文档。

有上限保护：单个 chunk 的字符数上限、单个文档的 chunk 数上限。超过上限时截断
并标记，而不是静默丢弃。

chunk key 是稳定的，所以重新索引同一份内容会原地更新而不是产生重复行。

## 空壳 chunk 问题

父标题紧跟子标题时，父标题这一节实际上只剩标题行，没有正文。这会产生
十几字节、零证据价值的 chunk。

修法是把只含标题的壳并入下一个有正文的 chunk，并保留更具体的那个标题路径。

### 不要激进合并

曾经尝试"合并所有过小的 section"，结果短文档退化成单个 chunk，标题定位
全部丢失，反而更糟。

判断依据是**是否有正文**，不是**是否够长**。一个 80 到 180 字的问答条目
本来就是合适的粒度，不需要合并。

## 链接图

同一个 revision 内，包内 Markdown 相对链接会被解析成文档级的链接图。
检索命中后可以沿链接扩展一跳邻居，用来补足上游定义。

链接只在 package 内解析。指向包外或指向不存在文件的链接会保留目标路径但
不解析成实际文档，这类悬空链接在体检时是有用的信号。

## 当前的粒度不对称

Skill 索引的是 L0 card，命中后按需展开正文；知识库索引的是 chunk 正文，
K0 catalog 卡片不参与检索。

这个不对称是分别演进出来的，不是设计的。两个后果：Skill 的召回上限被 card
措辞锁死；知识库缺少库级语义路由，库数量增长后 agent 无法先判断该查哪个库。

wiki 层就位后应重新评估检索对象——加速层目前装在 raw 层上。


## 分块上限与截断的处理

单个 chunk 的字符上限是 1200，重叠 120。上限不是按 token 算的，因为 token 数
依赖具体 tokenizer，把它写进存储层等于把供应商绑死在数据里。

超过上限时按标题层级先切，切不开再按段落切，最后才按字符硬切。硬切会在 chunk
元数据里标记 `truncated_at_boundary=false`，这样后续体检能把"被粗暴切开的
chunk"和"本来就短的 chunk"区分开——两者在检索命中率上的表现完全不同，混在一起
统计会掩盖分块质量问题。

一个 chunk 被硬切并不代表它没用，只代表它的边界不可信。引用它的 wiki 页面在
体检时应被优先复核。
